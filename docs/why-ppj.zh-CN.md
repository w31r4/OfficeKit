# OfficeKit 为什么使用 PPJ

PPJ（PPT Program JSON）是 OfficeKit 的声明式演示文稿源格式。`.ppj` 是严格的
UTF-8 JSON 文件，描述当前 deck 的沟通目标、设计语法、页面、有序元素、资产、
动效和源文件绑定。

本文解释 OfficeKit 为什么把通用 Agent 与有限的演示文稿语言分开。

[English](why-ppj.md) · [OfficeKit 所说的演示文稿是什么](what-is-a-presentation.zh-CN.md)

## 制作过程与产物不是一回事

制作 PPT 可能需要开放式工作：研究证据、计算数值、比较方案、寻找图片，并根据渲染
结果反复修改。通用 Agent 或编程语言适合完成这些工作。

某一版演示文稿本身不同。它的页数、对象、文字、资产、坐标、图层和关系都是有限的。
OfficeKit 需要检查、比较、编译、重开、复核和恢复这份状态。PPJ 直接描述这个有限产物。

```text
Agent 或可选脚本
  研究 · 推理 · 计算 · 生成
               ↓
              PPJ
  有限状态 · typed 对象 · 稳定身份
               ↓
      NativeAOT C# 编译器
               ↓
              PPTX
```

Agent 可以在 PPJ 外部使用图灵完备语言。PPJ 本身不需要任意计算能力。

## 这里所说的图灵完备是什么

在时间和内存足够时，图灵完备语言可以表达任何可计算过程。JavaScript 能分支、循环、
递归、动态创建数据并与外部系统交互。当执行路线无法预先确定时，这些能力很有用。

与此同时，我们无法写出一个程序，完美分析所有任意程序。停机问题展示了这个边界。
假设存在一个万能函数：

```text
willStop(program, input)
```

它声称能判断任意程序是否结束。现在构造 `contrary`，让它把自己同时当作 program 和
input 交给 `willStop`。如果预测会结束，`contrary` 就进入循环；如果预测不会结束，
`contrary` 就立即结束。两种答案都会推翻预测，因此万能的 `willStop` 不可能存在。

这不表示 JavaScript 不安全或不适用。工程系统可以使用超时、预算、中断和权限限制。
结论更具体：OfficeKit 无法在运行前，对任意程序同时完美证明它会结束、只修改声明范围、
产生确定输出并能安全恢复。

## 为什么演示文稿适合使用 DSL

PPJ 只接受有界的演示文稿结构：typed 元素、稳定 ID、有序数组、有限组件展开、本地资产
引用和明确的导入能力。它没有函数、递归、`while`、网络访问、raw OOXML 和任意表达式。

这个边界使 OfficeKit 可以在修改 PPTX 前完成以下工作：

- 完整解析并检查程序；
- 证明组件展开不会无限进行；
- 计算发生变化的节点和可能受影响的 package part；
- 对相同的有效输入进行确定性编译；
- 让全新 Agent 直接重开文件，而不用恢复 JavaScript 堆；
- 在破坏源文件前拒绝不受支持的导入修改；
- 把程序版本当作普通数据进行 diff、复核和恢复。

JSON 本身只是一种数据语法。OfficeKit 为它定义 schema、语义、验证、编译和复核契约后，
PPJ 才成为领域专用语言。

## 浏览器和电脑操作需要另一种分层

浏览器和桌面任务面对的是持续变化的开放环境。登录框、跳转、超时、弹窗和意外页面都
可能要求临时分支、重试或改变策略。因此外层适合使用通用控制器：

```text
观察 → 判断 → 行动 → 再次观察
```

单次动作仍然应该有界、typed，例如 `navigate`、`click`、`type`、`scroll`、`wait`
和 `screenshot`。控制器可以图灵完备，动作协议保持可审计。

演示文稿采用同样的分工，但边界不同：

| 层次 | 适合的形式 |
| --- | --- |
| 研究、规划、计算和迭代 | 通用 Agent 或可选脚本 |
| 持久演示状态 | PPJ |
| 导入文件的局部修改 | typed、source-bound Edit Plan |
| 原生文件生成 | 确定性 C# 编译器 |
| 观察与纠正 | 渲染和复核证据 |

结论不是所有场景都使用 DSL。开放世界的探索适合通用控制器，有限产物适合声明式源文件。

## 从零创建与第三方导入的权威不同

对于 OfficeKit 从零创建的 deck，PPJ 是源程序，PPTX 是编译产物。

对于任意第三方 PPTX，原始 package 仍然是未知原生内容的权威来源。OfficeKit 把已经
理解的对象投影成 typed PPJ 元素，通过 native reference 暴露有界的导入编辑能力。
未知子图继续保存在源包中。修改 PPJ 后，OfficeKit 生成经过验证的局部 Edit Plan，
而不是重建整个文件。

这种不对称是有意设计。Agent 可以使用统一、易读的编程表面，同时不声称已经完整
反编译所有 OOXML 能力。

## 预期工作流

```text
创建：deck.ppj → check → build → render → review → 修改
导入：deck.pptx → 投影 PPJ → 编辑 → 验证后局部 build
恢复：重开最近有效的 PPJ revision → inspect → 继续
```

PPJ 不是 JavaScript 的弱化替代品。它是智能、可适应的 Agent 与确定性原生演示文稿
编译器之间的稳定契约。
